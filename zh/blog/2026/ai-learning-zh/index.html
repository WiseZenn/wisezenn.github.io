AI 时代的学习与科研工作流

创建于 2026年09月23日

2026   ·   DevOps & Workflow

AI 让“做出来”变得容易了，但也容易让人跳过“想明白”。

以前复现一篇论文、写一个数值程序，可能要花几周时间；现在把需求描述清楚，Agent 很快就能给出一版能跑的代码。门槛降低是好事，但如果因此跳过基础，后面遇到问题时就会不知道从哪里下手。

我的体会是：基础要打，广度要有，剩下的交给 Agent 去执行和试错。

概念地图

学一个方向，最重要的不是背 API，而是理解范式。

比如面向对象、资源管理、并行计算、数值稳定性、内存层次，这些东西不会因为换了一个框架就失效。你不需要一开始就写出高性能代码，但要知道这些问题存在，知道什么问题该用什么工具。

这样在给 Agent 描述需求时，才能说清楚约束；在它给出方案时，才能判断是否合理。

学习顺序上，我建议先看官方文档和经典教材，再看博客和视频。官方文档更新最及时，质量也最稳定；博客和教程良莠不齐，适合用来补充直觉，不适合作为唯一依据。

“AI 时代学得慢就是学得快”这句话有一定道理。模型能力在快速进化，今天花很多时间记的 API，明天可能就变了；但概念、范式、调试思路不会那么快过时。

基础代码库

每个方向都有一些基础算法和流程。把它们实现出来，验证正确，整理成一个自己的代码库，是很有价值的积累。

这个过程可以借助 Agent，但不要完全交给它：

  1. 自己先想清楚输入、输出和边界条件；
  2. 让 Agent 生成第一版；
  3. 自己推导一遍关键公式，检查实现是否符合；
  4. 写测试，用简单案例验证；
  5. 再让 Agent 帮忙优化、重构、补文档。

代码库不需要很大，但要是“自己真的理解”的。以后遇到新问题，可以在这个基础上改，而不是每次从零开始。

也可以读实验室或团队里已有的代码。很多细节不会写在论文里，但会藏在代码里：怎么处理边界、怎么选参数、怎么加速。让 Agent 帮你读懂这些代码，再自己复述一遍，是很好的学习方式。

论文复现

读论文和复现论文，是两种不同的理解。

读的时候，你看到的是作者整理过的逻辑：问题、方法、实验、结论。复现的时候，你会遇到作者没写的细节：数据怎么预处理、参数怎么选、结果不好时怎么调。这些细节往往才是真正的手艺。

我的建议是：

  1. 选一篇和你方向相关、代码量可控的论文；
  2. 先读摘要、方法和实验设置；
  3. 让 Agent 帮你搭一个复现框架；
  4. 自己跑通 baseline，再逐步对齐论文结果；
  5. 记录差异，分析原因；
  6. 改一两个参数或条件，看看结果怎么变。

复现不一定要完全一样。很多时候，差异本身就是新问题的起点。为什么这个设置下效果好、换个条件就不行？这些问题会把你从“读论文的人”变成“做研究的人”。

Idea 落地

有了想法之后，我的建议是：先不要管别人是不是做过，先把它实现出来。

原因很简单：实现一遍的成本，现在主要就是 Token 和时间，而不是几个月的编程。你可以让 Agent 快速搭一个原型，跑几组实验，看看想法是否成立。等有了结果，再去查相关文献，对比差异。

这个顺序有两个好处：

  • 你对问题的理解会更深，因为你是从实现和结果出发的，不是从别人的结论出发的；
  • 即使别人做过，你也能说清楚自己的方案和他们的差异在哪里。

当然，查文献仍然重要。只是在实现之前查，容易被别人的框架限制；实现之后查，更容易看出真正的差异。

如果想法不可行，也不是白做。复盘一下为什么不可行、哪个假设出了问题，这些经验比一篇“看起来可行”的综述更有价值。

信息检索

AI 搜索很方便，但我不建议完全依赖它。

原因有几个：

  • 模型的数据库覆盖有限，很多论文和资料它访问不到；
  • 搜索结果可能有偏差，甚至被商业因素影响；
  • 它可能编造引用，尤其是参考文献、DOI 这类细节；
  • 长期只接受推荐内容，容易困在信息茧房里。

我的习惯是：让 AI 帮我生成关键词、梳理方向，然后自己去数据库检索，自己看摘要和结论。AI 可以加速这个过程，但不能替代判断。

阅读面也要宽一点。专业之外的书、其他领域的文章，常常能提供不同的视角。很多创新来自迁移和组合，而迁移的前提是你知道别处有什么。

Skill 沉淀

用 Agent 做久了，会发现很多任务是重复的：读论文、审查代码、整理笔记、写周报。这些流程都可以沉淀成 Skill。

比如文献阅读的 Skill，可以固定输出结构：

  • 研究问题；
  • 创新点；
  • 方法；
  • 实验设置；
  • 主要结论；
  • 局限和可扩展方向。

代码审查的 Skill，可以固定检查顺序：

  • 架构是否合理；
  • 边界条件是否处理；
  • 错误处理是否完整；
  • 测试是否覆盖关键路径；
  • 是否有明显的性能问题。

Skill 不需要一开始就很复杂。先把常用的提示词写下来，用几次，看看哪里不稳定，再逐步补充。等到流程稳定了，再考虑做成可复用的 Skill 或插件。

但不要过度封装。模型能力在变，流程也要跟着变。一个 Skill 如果让你每次都要额外解释、额外修正，那它可能已经不适合当前的模型了。

持续输出

我一直觉得，输出是学习闭环里最重要的一环。

写博客、做个人网站、整理笔记，都是在逼自己把模糊的理解变成清晰的表达。写不清楚，往往说明还没想清楚。而且这些内容会变成你的数字资产：以后让 Agent 帮你做事时，这些笔记、代码、文档都是可以复用的上下文。

个人网站也不需要等到“准备好”再做。找一个模板，托管在 GitHub Pages 上，先把第一篇文章发出去。有了输出的习惯，输入也会更有方向。

结语

AI 很强，但它的强建立在已有知识之上。真正的边界拓展，仍然需要人来提出问题、判断方向、承担结果。

所以我会说：让 Agent 成为你的执行助手、讨论对象、复习工具，但不要让 Agent 代替你思考。

保持好奇，保持质疑，保持思考。
